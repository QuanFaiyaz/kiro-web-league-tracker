# Graceful 503 for missing RIOT_API_KEY

The API route's error handler already caught 401/403 responses from the Riot API and returned a generic 503 to avoid leaking key-expiry details. This change extends that guard to also catch the case where `RIOT_API_KEY` is entirely absent from the environment — which surfaces as a `RiotApiError(500, "RIOT_API_KEY is not configured")` thrown by `riotFetch`. The condition now checks `error.status === 500 && error.message.includes('RIOT_API_KEY')`, funneling all three credential-failure modes into the same user-friendly 503 response.

**Watch for:** The string-matching condition is brittle — any refactor of the error message in `lib/riot-api.ts` silently breaks the catch (confirmed). The `recharts` dependency addition in the lockfile is unrelated to this fix (confirmed).

## High-level view

The functional change is a single expanded `if` condition. The design choice is to match by status code plus a message substring rather than introducing a distinct error subclass or a dedicated error code for missing configuration. This keeps the change minimal but couples the route handler to exact wording in `riotFetch`.

The lockfile also gained `recharts` and its full D3 dependency tree. This is unrelated to the API-key handling fix and inflates the diff without behavioral connection to the stated goal.

## Catch condition and message coupling

The expanded condition at line 201:

```typescript
if (error.status === 401 || error.status === 403 || (error.status === 500 && error.message.includes('RIOT_API_KEY')))
```

gates on two things for the missing-key case: a status of 500 and a substring in the message. `riotFetch` currently throws exactly `new RiotApiError("RIOT_API_KEY is not configured", 500)`, so the match works today. The risk is maintenance drift: if someone changes the message to `"Riot API key not set"`, the condition silently stops matching, and the error falls through to the generic handler that returns `{ error: error.message, status: 500 }` — leaking the internal "not configured" message to the client, which is the exact scenario this fix is trying to prevent.

A more durable approach would be to add a machine-readable discriminator — either an error code field on `RiotApiError` (e.g., `code: 'MISSING_API_KEY'`) or a separate `RiotConfigError` subclass that the route can `instanceof`-check. Both eliminate the string coupling without significantly increasing complexity.
