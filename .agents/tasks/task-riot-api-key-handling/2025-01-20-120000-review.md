# Missing API key now returns 503 instead of 500

The catch block in the Riot API route previously only mapped 401/403 errors to the user-friendly 503 response. When `RIOT_API_KEY` is absent, `riotFetch()` throws a `RiotApiError` with status 500 and message "RIOT_API_KEY is not configured". That error fell through to the generic `RiotApiError` handler, which echoed the internal message to the client. The fix adds a string-match condition on the error message so the missing-key case also returns the opaque 503.

**Watch for:** The detection relies on a substring match against an error message defined in a different file — a fragile coupling that can silently regress if the message text changes (confirmed).

## High-level view

The change is a single condition added to an existing `if` statement. It closes a gap where a server-side configuration error (missing env var) was leaking internal details to the client. The approach is minimal and solves the immediate problem, but ties the route's behavior to a magic string in `lib/riot-api.ts` with no compile-time guarantee that the two stay in sync.

## String-based dispatch and the coupling risk

The error originates in `lib/riot-api.ts:89`:

```typescript
throw new RiotApiError("RIOT_API_KEY is not configured", 500);
```

The route catches it at `app/api/riot/route.ts:201`:

```typescript
if (error.status === 401 || error.status === 403 || error.message.includes('RIOT_API_KEY')) {
```

There is no shared constant, no enum, and no type-level link between these two strings. A rename, rewording, or localization of the error message breaks the condition silently — the route would fall through to the generic handler and expose the raw message to the client, which is exactly the bug this fix is meant to prevent.

A more robust approach: check `error.status === 500` combined with an explicit error code or sentinel (e.g., a `code` field on `RiotApiError`), or simply match on status alone since no other 500-status `RiotApiError` is thrown today. Alternatively, hoist the message into a constant exported from `lib/riot-api.ts` and import it in the route.

## Status semantics

The thrown error uses status 500, indicating an internal server misconfiguration. The route remaps it to 503, a status conventionally meaning "upstream dependency unavailable, try again later." A missing env var won't resolve itself on retry — it requires a deployment fix. This isn't a blocking concern (clients don't distinguish between "come back later" and "broken until fixed" in practice), but it muddies monitoring if 503 alerts are treated as transient upstream failures.

## Test coverage

No automated tests cover this path. The project has no test framework configured, so this gap is systemic rather than specific to this change, but it's worth noting that the fragile string coupling described above would be the first thing a regression test should exercise.
